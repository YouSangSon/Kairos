# ADR-0002: DDD와 클린 아키텍처의 모듈 경계

- 상태: 설계 기준 채택. 기존 core의 전체 분리는 미완료.
- 날짜: 2026-11-04
- 근거: 유지보수·확장성을 위한 사용자의 DDD·클린 아키텍처·모듈화 요구. Go 유지.

## 책임과 의존성

하나의 배포 가능한 모듈형 모놀리스를 유지한다. 도메인별로 업무 용어와 불변식을 소유하고, HTTP·CLI·DB·브로커 구현이 도메인 안으로 들어오지 않게 한다. 폴더 수나 인터페이스 수를 늘리는 것을 완료 기준으로 삼지 않는다.

| 경계 | 소유 책임 |
| --- | --- |
| 원장 | 거래 사실, 정정, 정확한 금액과 FIFO 재생 |
| 포트폴리오 | 검증된 원장·가격·환율을 이용한 평가와 수익률 읽기 모델 |
| 주문·실행 | 주문 상태, 중복 방지, 실행 권한, 위험 예약, fencing과 복구 |
| 시장 데이터 | 가격·환율·상장 정보와 관찰 시점·출처 |
| 연구·모의 운용 | 재현 가능한 후보 평가, 모의 회계와 성과, 승인된 승격 절차 |

위 표는 책임 경계이며 곧바로 독립 DB나 서비스로 나누는 지시가 아니다. 브로커는 주문·시장 데이터 경계가 소비하는 외부 어댑터다. 위험 판단과 주문 예약의 기존 DB 트랜잭션 단위를 유지한다. 외부 주문 제출은 dispatch 기록을 커밋한 뒤 수행하며, 결과 불명 상태는 재제출하지 않고 reconciliation으로 복구한다.

각 모듈의 domain은 순수 규칙과 값·상태 전이를 소유한다. application은 사용 사례를 조합하고 트랜잭션·시간·ID·외부 호출의 경계를 소유한다. infrastructure는 application이 필요로 하는 작은 인터페이스를 SQLite·브로커로 구현한다. HTTP·CLI는 입력과 출력을 변환하고 application을 호출한다. 실행 진입점에서 실제 구현을 연결한다.

의존성은 외부 어댑터 → application → domain 방향이다. 다른 모듈의 테이블이나 내부 타입에 직접 접근하는 새 경로를 만들지 않는다. 읽기 모델은 명시적으로 소유한 조회 어댑터에서 조합한다. 모든 구조체에 인터페이스를 붙이거나 범용 repository·이벤트 버스를 먼저 만들지 않는다.

## 기존 계약 보존

- exact의 임의 정밀도 유리수, canonical decimal 문자열과 반올림 정책을 유지한다.
- 주문 이벤트의 JSON 필드 순서·생략 규칙·해시와 기존 복구 증명을 유지한다.
- 원장 반영·예약·실행 기록의 원자성, SQLite 단일 writer와 기존 마이그레이션을 유지한다.
- HTTP·CLI·백업 형식과 Flutter/Python 계약을 보존한다. 연구 모듈에 브로커 제출 권한을 넘기지 않는다.

## 적용 현황과 검증

현재 exact·orderdomain·paperdomain·riskdomain·researchdomain·strategydomain은 분리돼 있다. `internal/architecture/dependencies_test.go`는 이 여섯 패키지의 운영 소스를 재귀 검사해 승인된 순수 라이브러리와 도메인 의존성만 허용한다. 기존 `go test ./...`와 CI에서 실행한다. 표준 라이브러리도 SQL·HTTP·파일 시스템 접근이면 허용하지 않는다.

대부분의 저장소·사용 사례·HTTP 조합은 아직 `package main`에 있다. 다음 구현은 하나의 사용 사례씩 입력·출력·트랜잭션 계약을 고정하고 application과 어댑터를 함께 분리한다. 원장·주문·복구는 기존 특성 테스트와 백업 호환성 검증을 통과한 뒤 이동한다. 이 ADR과 의존성 검사만으로 전체 클린 아키텍처 전환 완료를 주장하지 않는다.

전체 프로젝트의 구현 전 상세 계약은 [전체 리팩토링 설계](../architecture/whole-project-refactoring.md)가 소유한다. 이 ADR은 책임 경계와 선택 이유를 유지하며 상세 파일 배치·전환 순서·실패 검증을 중복 정의하지 않는다.
